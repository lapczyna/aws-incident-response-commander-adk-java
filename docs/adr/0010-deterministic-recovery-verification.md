# ADR-0010: Recovery verification is deterministic, and the report is assembled by code

**Status:** Accepted · Phase 8

## Context

The plan named two LLM stages for closing an incident: a `recovery_verifier` and an
`incident_report_agent`. Building them showed both were the wrong shape, for the same reason and in
two different places.

**Verification.** Asking a model "did this work?" hands it the one judgement that determines whether
a human stops paying attention. It is also being asked while holding the transcript of its own
diagnosis and its own proposed fix, so it is marking its own homework. Models are agreeable in that
position, and the failure is invisible: a confident paragraph explaining that latency has returned
to normal looks identical whether or not it has.

**Reporting.** A model asked to produce a report with citations produces something that *looks*
cited. It will occasionally reference an observation it never read, renumber things between drafts,
or drop a citation when a conclusion feels obvious. None of that is visible in the prose. The
project's stated requirement is that every conclusion references stored evidence — and if the model
both writes the claims and chooses the citations, that requirement is unfalsifiable.

Simulator scenario 8 exists precisely for this: a convincing diagnosis, a reasonable rollback, and a
service that stays broken because the real cause was elsewhere.

## Decision

**The verdict is a numeric comparison performed in Java.** `RecoveryVerification.judge` takes the
value that motivated the incident, the value measured afterwards, and the threshold recovery is
defined against, and returns one of four outcomes. `RecoveryVerifierAgent` is a `BaseAgent` with no
model in it, exactly like `PolicyGateAgent` (ADR-0003), and it drives the incident to `RESOLVED` or
`FAILED` itself rather than leaving that to a caller.

**The report is assembled by Java; the model writes only the narrative.** The timeline comes from
the append-only audit log, the evidence table and its citation numbers from stored evidence rows,
the approval record from the approval tables, and the verification block from the stored
measurement. `ReportAgents.narrator` receives a pre-numbered evidence catalogue and is asked for
three prose sections and nothing else.

**Citations are checked, not trusted.** `IncidentReportRenderer.uncitedClaims` scans the narrative
for references that do not resolve to a stored observation and prints a warning *in the report*
naming them. An invented citation becomes a visible finding about the investigation rather than
invisible support for a claim.

## Four choices inside the verdict, each made against the flattering direction

| Situation | Outcome | Why not the alternative |
|---|---|---|
| Metric unreadable | `INDETERMINATE` | Treating "we could not measure" as success is the single most dangerous defaulting mistake available here. It is also not `NOT_RECOVERED`, which would blame a fix that may have worked. |
| Empty series | `INDETERMINATE` | For most sources an empty answer supports an inference. A service emitting no latency datapoints after a restart is more likely down than healthy. |
| Improved but still breaching | `PARTIALLY_RECOVERED` | Reporting it either way misleads. A metric that fell from 100× the threshold to 50× has halved and is still an outage, so improvement is measured against the distance back to the threshold, not as a ratio of raw values. |
| Asked too early | `TooSoonToVerifyException` | Not an outcome at all. Concluding `NOT_RECOVERED` because there is not yet enough post-remediation data would close an incident on the strength of impatience. |

Only `RECOVERED` permits resolution. Every other outcome sends the incident to `FAILED` and asks for
a human.

## Schema consequence

V1 modelled a verification as `recovered BOOLEAN`. That has no representation for "the metric could
not be read", and whichever value that case is forced into, the report lies. V4 replaces it with a
four-valued `outcome` plus the measurements the verdict was reached from — metric name, before,
after, threshold — so a reader can disagree with the conclusion without re-running anything.
`after_value` is stored as `NaN` rather than null when nothing was measured, because null invites a
reader or a query to treat it as zero, and a zero latency reads as spectacular recovery.

## Consequences

**Good.** The one judgement that ends an incident cannot be talked into a wrong answer, and it can
be unit-tested exhaustively — including the NaN case, which is a two-line test rather than an
evaluation run. The citation requirement becomes a property the renderer enforces. The sample
postmortem in `docs/samples/` is generated by the real renderer and compared against the committed
file by a test, so the documentation cannot drift from the code.

**Bad.** Verification needs criteria — which metric, what threshold — fixed when the incident is
raised. Deriving them from the alarm that fired is straightforward, but an incident raised without
them verifies as `INDETERMINATE` and lands in `FAILED`. That is the correct failure direction and it
is still a failure, and it means the quality of the alarm now bounds the quality of the verdict.

**Also bad.** A numeric threshold cannot express "the service is fine now, the metric is just noisy".
A human resolving such an incident by hand is the intended escape hatch, and there is deliberately no
way for the system to reach that conclusion on its own.
