# ADR-0011: Public-subnet Fargate with no NAT Gateway, and approval bound to an OIDC subject

**Status:** Accepted · Phase 10

## Context

The deployment had to satisfy two requirements that pull in opposite directions.

The first is that it must be **affordable to leave running**, because a demo nobody can afford to
leave up is a demo nobody sees. The second is that this is a system whose entire subject is
restraint — an approval gate, a policy engine, three independent layers enforcing one tag rule — and
a deployment that granted `AdministratorAccess` to a GitHub workflow would undercut every claim the
application makes about itself.

Two decisions turned out to carry the whole design, and both are trades rather than wins.

## Decision 1: Fargate tasks run in public subnets. There is no NAT Gateway.

A NAT Gateway in eu-west-1 is **$0.048/hour — about $35/month — before a single byte crosses it**.
The tasks it would serve cost $9/month combined on Spot. It would be the largest line item on the
bill by a factor of three, spent entirely on the privilege of the tasks not having addresses.

The tasks need egress: ECR to pull images, CloudWatch to ship logs, Secrets Manager at start-up, and
Bedrock or the Gemini API to think. Three ways to provide it:

| Option | Monthly | Verdict |
|---|---|---|
| NAT Gateway | ~$35 + $0.045/GB | Rejected. More than everything else combined |
| Interface VPC endpoints (ECR API, ECR DKR, Logs, Secrets Manager, Bedrock) | ~$36 | Rejected. *More* than the NAT Gateway it was avoiding |
| Public subnets, public IPs | $7.30 (2 × $0.005/hour) | **Chosen** |

**What this costs, and it is not money.** The tasks have routable IPv4 addresses. The only thing
between them and the internet is a security group, where in the rejected options there would have
been no path at all. That is a genuine reduction in defence in depth and it is not mitigated by
saying the security group is correct — security groups are correct until someone edits one.

The compensations are deliberate and small: `admin_cidr` defaults to empty and creates **no ingress
rule of any kind**, so the stack comes up reachable by nothing; the database sits in subnets with a
route table that has no routes in it, so there is no path out even if its security group were wrong;
and the demo target service — the one designed to misbehave — runs with a task role that has no
policies attached at all.

If this were production, the endpoints would win and the $36 would be irrelevant next to the cost of
the data. It is not production, and pretending the calculation is the same in both cases would be
the dishonest part.

## Decision 2: The GitHub OIDC trust policy binds to an *environment*, not to a branch

The usual pattern is to trust `repo:owner/name:ref:refs/heads/main`. It is the example in most
documentation and it is weaker than it looks: it means **any workflow running on main can deploy**,
including one added by a pull request that was merged without anyone reading the workflow file. The
protection is the branch protection rule, and the credential is available before any human looks at
the run.

This binds to `repo:owner/name:environment:aws-demo` instead. GitHub only issues a token with that
subject after the environment's protection rules have been satisfied — its required reviewers, in
particular. **The approval stops being a convention and becomes a precondition for holding
credentials.** A workflow that forgets `environment: aws-demo` does not deploy without approval; it
fails to authenticate.

That is the same shape as the application's own approval gate, and for the same reason: the check
must sit before the capability, not after it. An approval that can be skipped by a code path is a
log entry, not a control.

## What was rejected inside these decisions

**A permissions boundary on the deploy role.** The strongest form of "this role may only create
roles that are themselves limited". It was designed and then dropped: this phase is build-only with
no deployment to test against, and an untested boundary that blocks every apply is worse than a
correct-but-broader policy. The role is instead scoped by resource-name prefix, and the escalation
paths are closed with explicit denies. The boundary is the obvious next step for anyone running this
for real.

**Multi-AZ RDS.** Doubles the largest line item to protect data that is regenerated by re-running
the simulator. `rds.tf` says so in a comment that begins with the words "this is not highly
available".

**ARM64 tasks.** Graviton Fargate is about 20% cheaper and the base images support it, but building
ARM images means either QEMU emulation in CI, which is slow enough to be annoying, or ARM runners,
which are free only for public repositories. Deferred, and noted in `ecs.tf`.

**A dedicated database for the demo target service.** Locally it gets one, so that the
connection-pool-pressure scenario cannot starve the investigator along with the investigated. On AWS
that would be a second RDS instance — more than doubling the bill for one of nine scenarios — and
sharing the Commander's instance would make the scenario demonstrate the opposite of what it claims.
So the deployed target service has no datasource, and that one scenario is documented as unavailable
there.

## Consequences

**Good.** The steady-state bill is about $33/month and an afternoon's demo is about twenty cents,
which makes the honest recommendation ("deploy it, look at it, destroy it") also the cheap one.
Every expensive component is behind a flag that defaults to off, and the two that cannot be — the
database and the public addresses — are the two that are named first in `docs/cost.md`. The deploy
role cannot create a NAT Gateway, an EC2 instance, a Multi-AZ database or an IAM user even if a
future edit to the Terraform asks it to.

**Bad.** The tasks are addressable from the internet, and the security group is load-bearing in a
way it would not be behind a NAT Gateway. Anyone adapting this for anything real should reverse
Decision 1 first and treat the $36 as the cost of the architecture rather than an optimisation to
be made later.

**Also bad.** Destroying the stack destroys its budget alert with it, so the mechanism that watches
for forgotten resources is itself removed by the cleanup. `docs/deployment.md` recommends a standing
account-level budget outside Terraform, which is advice rather than enforcement — and advice is
exactly the weak form of control this project spends the rest of its time avoiding.
